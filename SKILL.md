# Agent Team Lite

Use one project orchestrator per Git repository, including all linked worktrees and sessions that use this skill. It may run at most two independent teams in parallel. Each active team uses at most one developer, one independent reviewer, and one additional feature worktree; dispatch requires both roles to be available. The orchestrator also performs serial shared integration. A worktree is a separate working folder managed by Git. Do not create integration worktrees or child worktrees.

Keep this package independent. Use only the host's native agent/file/process tools, Git, a standard shell, and the project's already available build tools when required. Do not load, reference, install, require, or invoke other skills, plugins, package collections, or design-tool dependencies as part of Lite. Do not load the full Agent-Team package to fill gaps.

Explain work using short, active sentences and consistent technical terms. Keep official command spelling. Apply the same communication and scope rules to each teammate.

Follow [message formatting and wordmark](references/output.md) for every user-facing message. Read [commands and settings](references/commands.md) before routing any invocation. Read [serialized runs and deployment](references/runs.md) before continuous scheduling, completion, or recovery.

## Route the limited command set

Use `$agent-team-lite` in Codex and `/agent-team-lite` in Claude Code. Clear plain-language equivalents work. These are skill instructions, not terminal commands.

| Action | Behavior |
| --- | --- |
| `help` | Read-only commands, defaults, examples, settings, and limits; no reservation, file changes, agent launches, dependencies, or work. |
| `settings [continuous=on/off] [auto-deploy=on/off]` | Read defaults, or save only explicit changes for future runs. |
| `start [modifiers] [-- task]` | Read readiness, reserve one available team record, plan one scoped task, then create its one feature worktree. With no task, take a ready unassigned item from the existing local task record; if none exists, report the missing scope. |
| `status [team]` | Read saved project/team phases, task progress, blockers, and next action. No mutations, agent messages, fresh checks, or interruption. |
| `pause [team]` | Stop new assignments and integration for the selected team, save notes, and stop affected writers safely. Keep its reservation and worktree reserved. |
| `resume [team]` | Continue the same unfinished team and worktree after reconciling actual files, pending operations, and surviving writers. Do not restart completed steps. |

Use the recorded team identifier only to select one existing team for status, pause, or resume; it is not a user-created namespace. Reject `all`, `with-preview`, `approve`, dependency setup, named-team creation, more than two teams, and Pro multi-team/lane commands as unsupported in Lite. `start` accepts a task description, not a new named-team namespace. Explain the supported action without performing an unsupported request.

A development request while a team is unfinished belongs to that team only when it clearly continues the same task. One independent task may be admitted only when one of the two named-team records is free and its owned repository-relative Git paths and resources do not overlap either active named team; otherwise it waits for safe completion and removal. A legacy 6.1 slot has no path/resource ownership data, so it blocks all named-team admission until it completes or is explicitly migrated with verified ownership. Continuous admission follows the recorded authorized queue under its reservation. Never silently replace an existing task or fall through to the full skill. Natural-language requests to pause or resume use the same rules as the commands.

## Reserve one of two team records before work

Read [state and ownership](references/state.md) before start, pause, resume, handoff, or integration. Use the bundled read-only `scripts/readiness.sh` before admission and `scripts/team-slot.sh` for reservation/integration state through a standard shell. Resolve the absolute installed skill path; run helpers from the target repository. They use the shared Git metadata directory, so switching worktrees does not create another team record.

Acquire a team record BEFORE allocating its worktree, starting agents, or changing project records. Read-only readiness comes first: confirm a committed base, task ownership/dependencies, developer and independent reviewer capacity, and the identity/availability of mandatory gates. Queue selection also requires a canonical task record; an explicit new task may create that record only after its team is admitted. When auto-deploy is requested, readiness requires the target, mechanism, authority, and intended revision. Readiness never installs dependencies, starts servers, creates previews, or runs tests. Refuse admission if two unfinished named teams exist, any unmigrated legacy 6.1 slot exists, repository-relative Git path/resource ownership overlaps or is unresolved, an operation lock is interrupted, or a readiness fact is unknown. Mandatory-gate results are collected before integration/deployment, not invented at admission. State the occupied task(s), phase(s), and concrete next action.

Never bypass refusal with another branch, directory, session, renamed state folder, another copy of the skill, or automatic deletion of state. A stale timestamp does not establish that writers stopped. Do not start a Lite team alongside known active or paused full Agent-Team work in the same repository. Inspect existing project records and worktree ownership first; uncertain ownership is a blocker.

The cooperative reservation records prevent more than two Lite teams within the same repository metadata. They do not police unrelated tools, independent clones, other machines, or arbitrary Git commands. Disclose this limit rather than promise a global process lock. If separate clones share the same project, use one designated checkout and do not start competing Lite work in another clone.

## Plan, develop, review, integrate

1. Read applicable project instructions and current Git changes. Resolve the primary checkout and existing planning files. Preserve user edits. Confirm a committed base exists and that the host can actually dispatch one developer and one reviewer. If unavailable, report the blocker; do not claim a team was started or automatically install dependencies.
2. After reserving a team record, write the scoped requirements, acceptance conditions, task ownership, and phase into `.agent-team-lite/TASKS.md` in the primary checkout. Reuse a suitable existing local task file by recording its canonical path, rather than keeping two live task ledgers. Record a short plan, next action, observed host/session, role/model/effort, input revision, mandatory gates, and readiness evidence in `.agent-team-lite/CONTEXT.md`. Only the orchestrator writes these records. Acceptance conditions describe the required result; they do not create a feature-testing stage.
3. Create exactly one feature branch/worktree for that team from its recorded input commit, or continue its recorded owned worktree. Check `git worktree list --porcelain` and ownership before creation. All feature source changes, repairs, and merge-conflict repairs occur there. Never use automatic per-agent worktree isolation. Existing unrelated user worktrees are preserved, not counted as Lite-created worktrees, and not used for a Lite team.
4. Follow [host dispatch](references/hosts.md). Use one project orchestrator and, per active team, at most one developer and one independent reviewer. Only the orchestrator spawns teammates. The developer writes the assigned feature files. The reviewer reads a stable revision and reports findings without changing source. Stop that developer's writes during its review. Do not add specialists, nested teams, documentation agents, test agents, or another integrator.
5. Implement the simplest change that satisfies the recorded requirements. For UI changes, reuse the existing components and visual conventions; consider readable text, labels, keyboard access, spacing, and error states during source review. Do not install design tools or add browser-review machinery.
6. Run a focused source review and repair loop. Check the diff against requirements, obvious defects, scope, and maintainability. Do not create or run feature/unit/integration/end-to-end tests, automate browser tests, or claim runtime/visual validation. Do not add feature-code documentation or a documentation pass. Normal task and resume records are retained. Existing mandatory project/CI gates still apply: report a conflict or blocked gate rather than disable it or claim it passed. Optional build, lint, or type checks are allowed only when they are already available and materially needed; never describe them as proof of feature behavior. If a command includes tests, do not run it as a disguised build check.
7. Have the developer address concrete findings and the same reviewer re-read the affected diff. After two failed attempts without useful progress, change the approach within the same team. If still blocked, record the blocker and ask one focused question. Do not grow the team or add repeated review panels.
8. The orchestrator integrates the reviewed feature revision into main through the project's authorized Git process. There is no dedicated integration worktree or integrator agent. Follow [integration](references/integration.md): acquire the shared integration gate, resolve conflicts in the existing feature worktree, re-review changed portions, and serialize changes to main. Preserve commit permissions and branch protection. Review success does not grant push, merge, or deployment permission.
9. Reconcile every requirement with source-review evidence and state the untested behavior clearly. Stop this team's writers/processes, preserve needed notes, and safely remove its feature worktree only after integration is confirmed and no unpreserved edits remain. Record the exact integrated revision and retained branch. Do not force-remove worktrees or delete user data. After removal and recorded integration, follow the run reference: finish that team only after any enabled deployment reaches an evidenced safe outcome. If integration, deployment, or removal remains blocked, retain that team’s record in its unfinished phase. Only explicitly enabled per-task auto-deploy through the existing authorized mechanism is included; no rollback or production cleanup.

## Preserve scope and recovery

Save short notes at phase changes, before pause, and when context is running low. Keep task status in the one task record; keep each team’s current phase, branch/worktree, agent ownership, observed host/model/effort/input revision, mandatory-gate and deployment evidence, decisions, blockers, and next action in CONTEXT.md. No shared mistake database, cross-team handoffs, preview server, preview approval, or background monitor is included.

`pause` applies to the selected team; if selection is ambiguous, report the live teams and request an identifier. If writers cannot safely stop yet, record “pause pending” in notes and keep the current phase; do not report paused prematurely. `resume` retains the same run and its current task, branch, and worktree when present. A new Codex or Claude Code session may continue after reconciling current files, pending operations, and writer liveness; recorded session identity is provenance, not a normal mutation gate. Prove a writer stopped only before replacing it or claiming an overlapping path. Between tasks, recover the recorded admission boundary. If a development worktree is unexpectedly missing, stop and report it; do not silently create a replacement or discard its reservation. A crash does not imply a pause or a completed checkpoint.

Finish with a concise report: changed result, reviewed scope, checks actually run, feature behavior not tested, integration state, and remaining blockers. Do not say “tested” or “deployed” when those actions were not performed.
