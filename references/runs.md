# Runs, evidence, and limited deployment

Read this before admission, continuous scheduling, completion, pause/resume, or auto-deploy. The existing canonical local task record remains the only task ledger. The orchestrator records a compact section for each team in the existing CONTEXT.md: team identifier, owner/session provenance, task-file path and authorized queue scope, effective continuous/auto-deploy values and sources, current task/phase/checkpoints, worktree and input revision, observed host and developer/reviewer model/effort, mandatory-gate observations, pause/hold reason, deployment evidence, and next action. These are durable observed facts, not a new registry or background service.

Up to two independent named teams may be active. Before `team-admit`, run `sh /absolute/installed/skill/scripts/readiness.sh [--ledger ABS_PATH] [--developer known|unknown] [--reviewer known|unknown] [--gates known|unknown] [--auto-deploy-target VALUE] [--auto-deploy-mechanism VALUE] [--auto-deploy-authority VALUE]`, then reconcile current worktrees, repository-relative Git path/resource ownership, pending operations, and live/unknown writers. Omitted readiness states report `unknown`; it is strictly read-only. An omitted `--ledger` defaults to the canonical task ledger in the primary checkout; an explicit task may create/reuse that record after admission. An interrupted `operation.lock` is blocked, not evidence of a completed operation. A legacy unfinished 6.1 slot consumes capacity but has no path/resource ownership: fail named-team admission closed until that run completes or an explicit verified migration records its ownership. `team-admit TEAM OWNER TASK ABS_WORKTREE OWNED...` records a new team only if capacity is available and every owned repository-relative Git path and resource is disjoint; each `OWNED` item is `path:REPOSITORY_RELATIVE_GIT_PATH` or `resource:ONE_LINE_ID`, and the worktree is separately recorded. Incomplete team records fail closed. The recorded OWNER is provenance, not a normal mutation gate. A new Codex or Claude Code session continues the same project using its normal team commands after reconciliation; prove a writer stopped only before replacement or reuse of its path/resource.

Continuous mode processes ready, authorized, unassigned tasks in the canonical record’s priority/order (stable task ID breaks ties). It may admit a second task only when independent ownership and reviewer capacity exist. Never invent tasks, treat backlog presence as authorization, expand queue scope, or start more than two teams. A single explicit task never expands into queue work. Shared integration is always serial.

## Per-team boundary

1. Complete source review and repairs, mandatory gates, and authorized integration of the exact reviewed revision. Record the reviewed commit, observed gate state, host/roles, and evidence; review does not authorize merge, push, or deploy.
2. Acquire the shared integration lock with `integration acquire TEAM` immediately before changing shared main; wait/hold if another team owns it. Release it with `integration release TEAM` after integration reaches its recorded safe outcome. Do not integrate while the lock is uncertain.
3. Stop that team’s developer/reviewer activity and owned writers. Preserve all files and notes. Safely remove its feature worktree and confirm it is unregistered. Keep its branch unless deletion is separately authorized.
4. Record the exact integrated commit and cleanup evidence. Use `team-finish TEAM FULL_INTEGRATED_COMMIT retain` from cleanup to enter `between`; it retains the team while deployment disposition is pending. After independently observing the provider receipt and required gates, use `team-closeout TEAM FULL_INTEGRATED_COMMIT TARGET AUTHORITY RECEIPT OUTCOME` to record the exact revision and explicit deployment disposition. OUTCOME is exactly `succeeded` or `disabled`: for `disabled`, TARGET, AUTHORITY, and RECEIPT are each the literal `disabled`; for `succeeded`, all three are nonempty and not `disabled`. `team-finish TEAM FULL_INTEGRATED_COMMIT` releases only from `between`, with a matching valid closeout and no integration lock. A legacy continuous team instead uses its compatible `finish OWNER COMMIT retain` / `next OWNER TASK ABSOLUTE_FEATURE_PATH` boundary. A completed team may free capacity while another independent team remains active.
5. If a team is blocked, missing authority, has unresolved ownership, or has an uncertain operation, call `team-hold TEAM REASON` when safely possible. Retain its record and report the concrete next action. Do not busy-poll or promise work after the host ends.

## Deployment, only when enabled

After the exact completed, integrated, cleaned-up revision, use only the project’s existing deployment mechanism and established destination authority. Before submission record team/task ID, exact integrated revision and intended deployment revision, target, authority pointer, mechanism/command, known mandatory gates, and pending outcome. Verify that the mechanism will deploy that exact revision; dirty files, authority mismatch, or revision drift block deployment.

Observe the command/provider receipt and required gates, then record a `succeeded` or explicitly authorized `disabled` disposition and the actual deployed revision with `team-closeout`. The helper records the receipt; it is not independent proof that the provider deployed the revision or gates passed. This is deployment outcome evidence, not production testing or feature validation. No deployment with auto-deploy off. No batching, provisioning, plugin installation, rollback automation, production testing, or production cleanup. Enabling deployment never authorizes an unknown destination, bypasses mandatory gates, or grants destructive permissions.

On failure or uncertain/in-flight outcome, record recovery identifiers/output, exact revision, reason, and next action; hold only the affected team. Do not call `team-closeout` or release the team until the disposition is independently evidenced. Do not automatically retry, skip its task, or release its ownership. Resume inspects the existing receipt/provider evidence before any retry, avoiding duplicate submission. A confirmed success is recorded without redeploying. Retry only after the concrete cause is resolved and retry authority exists; otherwise remain held. A deliberate disable can leave the task integrated but undeployed only after resolving in-flight ambiguity and recording the authorized disabled disposition. Never claim deployment success without exact-revision evidence.

## Pause and recovery

Record pause intent immediately for the selected team, before waiting for writers or an in-flight integration/deployment to reach a safe outcome. Intent blocks that team’s admission and submission even before its phase becomes paused. Observe already submitted operations safely; do not pretend to cancel them. Use `team-phase TEAM paused` only once affected activity stops; otherwise report pause pending. Pausing one team does not pause an independent team.

Resume reconciles the selected team’s actual Git/worktree state, surviving agents, pending admission, deployment receipt, and integration-lock state. `team-phase`, `team-hold`, `team-recover`, and `team-finish` use the recorded TEAM; a prior session token is not a normal transition gate. `team-adopt TEAM NEW_OWNER` updates provenance only and is never required for ordinary same-project continuation. Never clear a deployment hold merely because the user said resume. Reconcile a crash after integration, removal, or deployment without repeating completed actions. Missing development work remains a blocker; missing worktree is expected only after evidenced cleanup.

After successful explicit resume, clear the selected team’s recorded pause intent before eligible work continues. Restore independent holds unchanged; clearing pause intent never clears deployment failure, missing authority, uncertain ownership, or an uncertain shared integration lock. If reconciliation fails, retain the intent and report the blocker. The host session owns execution; no background scheduler is created.
