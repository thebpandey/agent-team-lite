# Integration by the orchestrator

Keep main for planning, shared records, and receiving the integrated result. Do all feature edits and conflict repairs in the existing feature worktree. Do not create an integration worktree. Up to two teams may prepare independently, but shared-main integration is always serialized with `integration acquire TEAM` and `integration release TEAM`. The integration lock names the current team, not a session owner; inspect `integration show` and reconcile an interrupted operation before taking any shared-main action.

1. Stop this team’s developer writes. Confirm its independent reviewer approved the actual source revision and there are no unresolved findings. Record the actual reviewed revision, observed host, developer/reviewer model/effort, and mandatory-gate result in CONTEXT.md. Respect the project's permission to commit. Uncommitted changes are not a merge-ready revision.
2. Check the main checkout's branch, HEAD, dirty files, and pending Git operations. Main means the project's actual primary branch, which may have another name. Do not switch a user's unrelated checkout or stash their changes silently. Shared planning notes can remain uncommitted only when they will not be overwritten by the authorized integration method; otherwise preserve them and resolve the concrete blocker.
3. If main advanced, merge or rebase its current committed base into the feature branch under project rules, in the same feature worktree. Resolve conflicts there. Re-review affected source. Record the exact feature commit and observed main commit.
4. Acquire `integration acquire TEAM` immediately before changing main. For local integration, prefer a permitted fast-forward from the clean, correctly checked-out primary branch to the reviewed feature commit. Recheck main immediately before changing it; if it changed, return to step 3. Never force-update main. For protected branches, use the established pull-request process and wait for required approval/CI; no direct-push bypass. Keep that team reserved while waiting. The orchestrator remains the integration owner even when GitHub performs the actual merge.
5. Record proof that the reviewed change reached the primary branch. For a fast-forward or merge, verify ancestry. For a squash/rebase merge, record the merged PR, mapped primary revision, and source comparison evidence. Release with `integration release TEAM` only after the shared-main operation reached its recorded safe endpoint (integrated, or safely held/returned) and the main writer stopped. The lock release does not prove that endpoint itself. Do not pass an unrelated primary commit to a helper as a substitute for this evidence.
6. Stop that team’s agents and owned processes. Confirm the feature worktree contains no unpreserved tracked, untracked, or ignored files. Use normal safe `git worktree remove`, never forced removal. Retain the branch unless its deletion is separately authorized. A failed cleanup keeps that team reservation active.
7. Write completion, exact integration evidence, mandatory-gate observations, checks/limitations, and removal result into the canonical task/resume notes. Use `team-finish TEAM FULL_INTEGRATED_COMMIT retain` after cleanup to enter `between`. Do not release until the deployment disposition is independently evidenced and recorded by `team-closeout TEAM FULL_INTEGRATED_COMMIT TARGET AUTHORITY RECEIPT OUTCOME`; OUTCOME is exactly `succeeded` or `disabled`, with literal `disabled` for all three evidence fields in the latter case. Its helper receipt does not prove review quality, mandatory gates, or provider outcome. Follow [run completion](runs.md) for deployment closeout and legacy continuous compatibility.

Do not start a new task merely because a feature is reviewed, committed, or waiting for a merge. An independent second named team may be admitted only when there is capacity and no owned repository-relative Git path/resource overlap; an unmigrated legacy 6.1 slot blocks named-team admission because it has no ownership evidence. Internal continuous admission requires integration, stopped writers, worktree removal, and any enabled deployment for that team. Never let parallel feature work bypass the shared integration lock.
